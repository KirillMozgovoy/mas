Исследование механизмов распределения задач и координации

<b>Группа:</b> Б24-517

1. Задача и цель

Исследуется МАС доставки из ЛР1: источник формирует заказы, диспетчер распределяет их между курьерами, а курьеры принимают назначения, забирают и доставляют груз. Цель - сравнить механизмы распределения по времени обслуживания и стоимости координации на одинаковых входных данных.

Реализованы три варианта: централизованный round_robin (RR), централизованный выбор минимальной оценки маршрута nearest (MIN), контрактная сеть contract_net (CNET). Прототип сохранён в отдельной папке lab2, работа lab1 не изменяется.

Критерии исследования

Проверить влияние механизма на завершение 60 заказов, среднее и хвостовое время доставки, опоздания и пройденный путь. Отдельно измерить все сообщения и сообщения координации, оценить их объём. Проверить влияние нагрузки и числа агентов.

Архитектура

Источник и диспетчер имеют разные роли; курьеры являются самостоятельными агентами. Каждый хранит позицию, скорость, грузоподъёмность и состояние исполнения. Курьер самостоятельно отклоняет назначение при занятости или превышении массы. FIFO-шина доставляет сообщения в одном процессе; прямое изменение состояния другого агента не используется.

Источник требований: "Лабораторные-МАС.pdf", с. 1-2. Требования ЛР2: реализация и экспериментальное сравнение не менее двух механизмов, анализ времени выполнения, сообщений и затрат координации. Исходники и демонстрация: https://github.com/KirillMozgovoy/mas/tree/main/lab2

2. Механизмы и протоколы

Общие правила

Очередь заказов сортируется по времени поступления, затем по ID. Один курьер выполняет один заказ. Время дискретное; расстояние манхэттенское. За такт курьер проходит не более speed единиц пути, сначала по x, затем по y. Погрузка и выгрузка мгновенные, завершение фиксируется в конце такта. При равенстве оценок выбирается минимальный ID.

| Механизм | Выбор исполнителя | Обмен при назначении |
| --- | --- | --- |
| RR | По циклическому указателю среди свободных курьеров с достаточной грузоподъёмностью. Указатель сдвигается после выбора. | ASSIGN -> ACCEPT |
| MIN | Диспетчер минимизирует (d(позиция, получение) + d(получение, доставка)) / speed. Использует профили и STATUS. | ASSIGN -> ACCEPT |
| CNET | Курьеры рассчитывают ту же оценку локально. Диспетчер выбирает минимальную полученную заявку. | CFP -> PROPOSE / REFUSE -> ASSIGN / NOT_SELECTED -> ACCEPT |

Контрактная сеть

Для каждого ожидающего заказа диспетчер рассылает CFP всем курьерам. Свободный подходящий курьер отвечает PROPOSE с оценкой маршрута, остальные - REFUSE. Из предложений выбирается победитель; остальные участники получают NOT_SELECTED. Победитель получает ASSIGN и подтверждает его ACCEPT. Если предложений нет, заказ остаётся в очереди.

Раунды обрабатываются последовательно и завершаются в рамках одного такта. Подтверждение назначения выполняется до следующего раунда, поэтому один курьер не выигрывает два одновременных заказа. При пустом раунде запрос повторяется на следующем такте. Это упрощённый синхронный вариант контрактной сети; таймауты, встречные предложения и сетевые потери не моделируются.

Выполнение общего заказа: REQUEST -> назначение -> ACCEPT -> PICKED_UP -> DELIVERED. STATUS передаёт актуальную позицию и занятость после каждого активного такта. Повторный ASSIGN принятого заказа не запускает второе исполнение.

3. Методика эксперимента

| Параметр | Значение |
| --- | --- |
| Размер серии | 3 режима x 2 размера парка x 20 seeds x 3 механизма = 360 прогонов |
| Заказы | 60 на прогон; масса равномерно от 1 до 6, координаты от 0 до 19 по каждой оси |
| Поступление | sparse: один заказ раз в 4 такта; stream: каждый такт; burst: все 60 в такт 0 |
| Срок доставки | release + 35; опоздание не отменяет исполнение |
| Парк | 3 или 6 курьеров. Профили (capacity, speed): (3,1), (6,1), (4,2), с повторением для 6 |
| Генератор | random.Random(seed), seed = 0..19. Исходные позиции также случайные |
| Горизонт | 5000 тактов; остановка после завершения всех заказов |
| Связь | Надёжная FIFO; нулевая задержка; обработка сообщений не расходует модельные такты |

Для каждого сочетания нагрузки, размера парка и seed один и тот же набор передаётся всем трём механизмам. Наборы и SHA-256 сохранены в results/inputs.json.gz, построчные метрики - в runs.csv. Случайность касается входов; сами механизмы детерминированы. Название sparse означает только больший интервал поступления и не гарантирует отсутствия перегрузки.

Определения метрик

T - время от такта 0 до последней доставки. L - среднее время заказа (completion - release). P95 - элемент с номером ceil(0.95n) в отсортированном списке длительностей. Late - число completion > deadline. Путь - сумма пройденных курьерами единиц расстояния.

M - все сообщения. C - CFP, PROPOSE, REFUSE, NOT_SELECTED, ASSIGN, ACCEPT и REJECT; события выполнения и STATUS в C не включены. V - сумма длин компактных JSON-представлений сообщений C в байтах UTF-8, включая отправителя, адресата, время и данные. Это оценка объёма обмена без заголовков сетевого транспорта. CV - стандартное отклонение числа назначений между курьерами, делённое на среднее.

Для каждого показателя сохранены среднее, выборочное стандартное отклонение и ориентировочный 95%-й t-интервал среднего: mean +/- 2.093 * sd / sqrt(20). Для сравнения RR и MIN использованы парные разности на одинаковых seeds. Время процессора и стоимость в рублях не измеряются.

У RR и MIN C = 120: одно назначение и одно подтверждение на каждый из 60 заказов. У CNET много отказов и повторных раундов, пока курьеры заняты. Для одного раунда при n курьерах и b предложениях: 2n сообщений запроса и ответа; при b > 0 ещё b - 1 уведомлений проигравшим и 2 сообщения назначения и подтверждения, итого 2n + b + 1. При b = 0 - ровно 2n.

Число сообщений CNET зависит от длительности очереди, а не только от числа доставок. Нулевое время связи скрывает эти затраты в показателях T и L. Поэтому равенство времени выполнения не означает равную вычислительную или сетевую стоимость. CV учитывает только количество заказов, без их массы и длины маршрута; он не является полной мерой справедливости.

Отрицательная разность означает меньшее время заказа у MIN. Небольшие средние отличия нельзя считать универсальным преимуществом: проверять следует парные интервалы. Для парка из 3 курьеров очередь и ограничения массы во многом определяют назначения; локальная минимизация маршрута не оптимизирует весь план и может ухудшить будущие назначения.

Выводы

1. Реализованы и экспериментально сравнены три механизма, включая два различных протокола координации: прямое централизованное назначение и контрактная сеть с локальными заявками курьеров.

2. При полной актуальной информации, нулевой задержке и общей целевой функции MIN и CNET одинаковы по доставке. Контрактная сеть не даёт выигрыша в этих условиях, но создаёт существенно больше сообщений из-за рассылок и повторов.

3. На исследованных входах увеличение парка оказывает более сильное влияние на задержки, чем смена RR на MIN. Дедлайны напрямую не участвуют в выборе заказов, поэтому при перегрузке доля опозданий высока.

4. Для данной модели рационально централизованное MIN: оно обеспечивает ту же доставку, что CNET, при меньшем обмене. При приватных либо меняющихся знаниях курьеров контрактная сеть может быть полезна, но её преимущество в этой работе не доказано.

Ограничения и продолжение

Результаты относятся к данной сетке, генератору и профилям. CNET использует частые повторы без backoff; оптимизация повторов требует отдельного сравнения. Нет задержек связи, отказов, затрат на обработку сообщений и планирования нескольких заказов. Возможное продолжение - событийный повтор CFP, модель сети и учёт дедлайнов. Эти изменения не входят в выполненные эксперименты.
